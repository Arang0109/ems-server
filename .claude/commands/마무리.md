변경 내역을 추적하고 아키텍처 원칙 준수 여부를 검토한 뒤 보고합니다. 승인 후 커밋하고 푸시합니다.

---

## Step 1. 변경 내역 수집

다음 명령을 실행하여 변경 내역을 수집합니다:

```powershell
git status
git diff HEAD
```

- 변경 파일이 없으면("nothing to commit, working tree clean") → "커밋할 변경 사항이 없습니다." 출력 후 종료합니다.
- Untracked 파일은 `git diff HEAD`에 포함되지 않으므로, `git status`에서 새 파일 목록을 별도로 파악합니다.
- 신규 파일(Untracked/Added)은 Read 도구로 내용을 직접 읽어서 검토합니다.

---

## Step 2. 아키텍처 원칙 검토

수집한 변경 내역을 바탕으로 다음 체크리스트를 **항목별로** 검토합니다.
각 항목은 ✅(준수) / ⚠️(경미한 위반, 개선 권장) / ❌(위반) 중 하나로 판정합니다.

### 체크리스트

#### [A] 레이어 의존성
- [ ] `presentation` 계층이 `infrastructure`를 직접 참조하지 않는가?
- [ ] `application` 계층이 `infrastructure`(JPA Repository 등)를 직접 import하지 않는가?
- [ ] `domain` 계층에 `@Entity`, `@Column`, `@Repository` 등 JPA 어노테이션이 없는가?
- [ ] `domain` 계층에 Spring Framework(`@Component`, `@Service` 등) 어노테이션이 없는가?

#### [B] 포트 & 어댑터
- [ ] Application Service가 Spring Data Repository를 직접 주입받지 않고 Outbound Port를 통해 접근하는가?
- [ ] 신규 Outbound Port가 `application/port/out/`에 있는가? (`domain/port/`는 auth·contract 잔존분 전용이며 신규 금지)
- [ ] 신규 Inbound Port(UseCase)와 공개 VO(`~Summary`)가 `application/port/in/`에 있는가? (`port/` 직하 금지)
- [ ] 타 모듈을 참조할 때 그 모듈의 `port/in`만 쓰는가? (`port/out`·엔티티·JPA Repository 직접 참조 금지)
- [ ] 신규 Repository Adapter가 `{도메인}RepositoryAdapter` 네이밍을 따르는가?
- [ ] 단건 조회 Port 메서드가 `Optional`을 반환하지 않고(`T` 직접 반환), Adapter에서 `orElseThrow`를 처리하는가?

#### [C] 매핑 규칙
- [ ] 컨트롤러·서비스에서 직접 매핑하지 않고 MapStruct 매퍼를 사용하는가?
- [ ] Presentation 매퍼는 `presentation/mapper/`에, Infrastructure 매퍼는 `infrastructure/mapper/`에 위치하는가?
- [ ] 매퍼 메서드명이 컨벤션(`toCreateCommand`, `toUpdateCommand`, `toResponse`, `toEntity`, `toDomain` 등)을 따르는가?

#### [D] 네이밍 컨벤션
- [ ] 클래스명이 역할별 패턴(`{도메인}Controller`, `{도메인}Service`, `{도메인}Entity`, `{도메인}Document` 등)을 따르는가?
- [ ] Request DTO는 `{동작}{대상}Request`, Response DTO는 `{대상}Response` 형태인가?
- [ ] Response DTO 이름에 UI 컴포넌트(`Table`, `Grid`, `Card`, `Chart`, `Board`)가 포함되지 않는가?
- [ ] VO 접미사가 체계(`~Result`/`~ListItem`/`~Detail`/`~Summary`/`~ExportView`/`~Event`)를 따르는가?
- [ ] Command · VO가 Java Record로 작성되었는가? (`~ExportView`만 예외 — jxls가 getter로 해석)
- [ ] Command · VO가 `application/command/` 패키지에 위치하는가? (공개용 `~Summary`는 `port/in/`)

#### [E] 도메인 모델 패턴
- [ ] 도메인 모델이 정적 팩토리 메서드를 사용하는가? (생성자 직접 사용 금지)
- [ ] 수정 메서드가 `update()` + `toBuilder()` 패턴으로 새 인스턴스를 반환하는가?
- [ ] 도메인 모델에 `@Builder(toBuilder = true) + @Getter + @AllArgsConstructor + @NoArgsConstructor` 조합이 사용되었는가?

#### [F] tenant 소유권 격리 (멀티테넌시)

> 이 항목의 위반은 컨벤션 문제가 아니라 **교차 테넌트 취약점**입니다. 발견되면 종합 판정을 ❌로 합니다.

- [ ] tenantId를 `@AuthenticationPrincipal`에서만 얻는가? (path·header·body로 받지 않는가?)
- [ ] 컨트롤러가 받은 `principal.getTenantId()`를 **실제로 서비스에 전달**하는가? (파라미터만 선언하고 쓰지 않는 경우 ❌)
- [ ] 조회·수정·삭제 Port 메서드가 `(id, tenantId)`를 받는가? 전역 리소스(`PollutantCatalog`·`Tenant`·`Role`) 예외인가?
- [ ] Adapter/JpaRepository의 WHERE 절에 `tenant_id`가 포함되는가? 삭제는 `deletedCount == 0`을 `NOT_FOUND`로 처리하는가?
- [ ] 소유권 불일치를 403이 아니라 **404**로 은닉하는가?
- [ ] 부모 id를 파라미터로 받는 목록 조회가 그 부모의 tenant 소속을 확인하는가?
- [ ] 역할을 부여·변경하는 경로가 `UserValidator.requireAssignableRole`을 지나는가?

#### [G] 공통 규칙
- [ ] 모든 엔드포인트가 `ApiResponse<T>`를 반환하는가? (바이너리 다운로드·SSE는 예외 — 컨트롤러 javadoc에 근거가 있는가?)
- [ ] 생성자 주입에 `@RequiredArgsConstructor`를 사용하는가? (필드 주입 금지)
- [ ] `global` 패키지에 기능성 코드가 추가되지 않았는가? (`global/common/enums/`는 **둘 이상**의 모듈이 공유하는 enum만)
- [ ] 신규 Controller에 `@Tag(name = "...", description = "...")` 어노테이션이 있는가?
- [ ] ErrorCode가 컨벤션(`{DOMAIN}_{CONDITION}` 또는 범용 `{CONDITION}`)을 따르는가? 인라인 메시지 override는 동적 값이 필요한 경우인가?
- [ ] 컬럼·제약·테이블을 **삭제**했다면 `docs/migration/`에 수동 스크립트를 남겼는가? (`ddl-auto: update`는 삭제를 반영하지 않음)
- [ ] 새 테스트가 프로젝트 표준(Fake 리포지토리 + 생성자 직접 조립 + AssertJ)을 따르는가?

## Step 3. 검토 보고서 출력

다음 형식으로 검토 보고서를 출력합니다:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
아키텍처 검토 보고서
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
변경 파일 (<N>개):
  - <파일 목록>

[A] 레이어 의존성      : ✅ / ⚠️ / ❌
[B] 포트 & 어댑터      : ✅ / ⚠️ / ❌
[C] 매핑 규칙          : ✅ / ⚠️ / ❌
[D] 네이밍 컨벤션      : ✅ / ⚠️ / ❌
[E] 도메인 모델 패턴   : ✅ / ⚠️ / ❌
[F] tenant 격리        : ✅ / ⚠️ / ❌
[G] 공통 규칙          : ✅ / ⚠️ / ❌

──────────────────────────────────────────
지적 사항:
  1. [항목] <파일명> — <위반 내용 및 개선 방법>
  (없으면 "지적 사항 없음"으로 표기)

종합 판정: ✅ 이상 없음 / ⚠️ 경미한 문제 / ❌ 위반 있음
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

보고서 출력 후 다음 질문을 합니다:

> **커밋을 진행할까요?**
> - `y` / `yes` → Step 4로 진행합니다.
> - `n` / `no`  → 종료합니다. 문제가 있다면 수정 후 다시 실행하세요.
> - 커밋 메시지를 직접 입력하면 해당 텍스트를 그대로 사용합니다.

종합 판정이 ❌(위반)인 경우에도 사용자가 `y`로 승인하면 커밋을 진행합니다.
단, 보고서에 "⚠️ 위반이 있음에도 진행합니다." 문구를 포함합니다.

## Step 4. .env 파일 안전 검사

`git status` 결과에서 `.env`, `.env.local`, `.env.production` 등 `.env*` 패턴의 파일이 포함되어 있는지 확인합니다.

해당 파일이 있으면 **즉시 중단**하고 출력합니다:
"위험: `.env` 파일이 변경 목록에 포함되어 있습니다. 보안 정보 노출 방지를 위해 커밋하지 않습니다."

---

## Step 5. 커밋 메시지 결정

- **사용자가 직접 메시지를 입력한 경우**: 해당 텍스트를 그대로 사용합니다.
- **`y` / `yes`로만 승인한 경우**: `git diff HEAD` 결과를 분석하여 자동 생성합니다.
  - 형식: `type: 변경 내용 요약 (한국어)`
  - type 종류: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style`
  - 변경 범위가 여러 모듈에 걸치면 가장 핵심적인 변경을 대표로 선택합니다.

---

## Step 6. Staging & Commit

```powershell
git add .
git reset HEAD -- .env
git reset HEAD -- .env.local
git reset HEAD -- .env.production
```

PowerShell 환경에서 Co-Authored-By 태그를 포함해 커밋합니다:

```powershell
git commit -m "<커밋 메시지>`n`nCo-Authored-By: <현재 세션의 모델명> <noreply@anthropic.com>"
```

---

## Step 7. Push

현재 브랜치명을 확인한 후 push합니다:

```powershell
git push origin <현재-브랜치명>
```

- **성공** → 최종 결과를 출력합니다.
- **실패 (non-fast-forward)** → `git pull --rebase origin <브랜치명>` 후 재시도를 권고합니다.
